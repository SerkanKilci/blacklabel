# Blacklabel

Barcode scanner for packaged food: analyzes ingredients, additives and allergens, and produces a 0-100 score. See the original spec for full product/API/data model details.

## Structure

```
backend/    .NET 8 Web API (Domain / Application / Infrastructure / Api) + xUnit tests
backend/tools/OffImporter/  Console ETL: bulk-imports target-market products from the OFF data dump
mobile/     Expo (React Native + TypeScript) app, expo-router navigation
```

## Backend

Requirements: .NET 8 SDK, Docker (for SQL Server), `dotnet-ef` tool (`dotnet tool install --global dotnet-ef`).

```bash
cd backend
docker compose up -d                     # starts SQL Server on localhost:1433
dotnet user-secrets set "ConnectionStrings:DefaultConnection" \
  "Server=localhost,1433;Database=Blacklabel;User Id=sa;Password=YourStrong!Passw0rd;TrustServerCertificate=True" \
  --project src/Blacklabel.Api
dotnet ef database update \
  --project src/Blacklabel.Infrastructure \
  --startup-project src/Blacklabel.Api
dotnet run --project src/Blacklabel.Api
```

API comes up at the URL printed in the console (see `src/Blacklabel.Api/Properties/launchSettings.json`), with Swagger UI at `/swagger` (use the "Authorize" button with a token from `POST /api/v1/auth/device` — **every** endpoint requires it, except the RevenueCat webhook) and a health check at `/api/v1/health`. Resources: additive dictionary (`GET /api/v1/additives`, `GET /api/v1/additives/{code}`), product lookup (`GET /api/v1/products/{barcode}`) and alternatives (`GET /api/v1/products/{barcode}/alternatives`, premium-only), contribution flow (`POST /api/v1/products/{barcode}/contribute`), device/account auth (`POST /api/v1/auth/device`, `POST /api/v1/auth/link`), profile and preferences and subscription status (`GET /api/v1/me/profile`, `GET`/`PUT /api/v1/me/preferences`, `GET /api/v1/me/subscription`), scan history (`GET`/`POST /api/v1/scans`, paginated + batch), and the RevenueCat webhook (`POST /api/v1/webhooks/revenuecat`).

By default `VisionService:Endpoint` is empty, so contributions will always come back as "vision failed" until you point it at your own vision-LLM proxy that returns the JSON shape documented in `HttpVisionService.cs`. Set it via `VisionService:Endpoint` in `appsettings.json` or an environment variable. Similarly, `RevenueCat:WebhookSecret` (a user-secret, matching the "Authorization header value" configured in the RevenueCat dashboard's webhook settings) must be set for the webhook to accept requests — it fails closed (401) when unset.

`POST /api/v1/auth/link` (Apple/Google account linking) verifies the client-supplied identity token server-side before trusting anything in it: `AppleIdentityTokenVerifier`/`GoogleIdentityTokenVerifier` (`src/Blacklabel.Infrastructure/Auth/`) fetch each provider's live JWKS via its OIDC discovery document and check signature, issuer, audience and expiry with `Microsoft.IdentityModel`; only the `sub`/`email` claims from a token that passes are ever written to `AppUser`. Audiences are configured via `Auth:Apple:BundleId`/`Auth:Google:ClientId` in `appsettings.json` (public identifiers, not secrets) — both are empty by default, and an empty audience makes that provider's verifier fail closed (every link attempt rejected) rather than skip the check, the same posture as the RevenueCat webhook secret above.

**Server-side limits (§11)**: free accounts get 10 barcode scans/day (`GET /products/{barcode}` returns 429 past that; every successful lookup — cached or freshly fetched — records the authoritative `Scan` row used for counting) and 2 label-photo analyses/day (`POST .../contribute` returns 429); scan history (`GET /scans`) is capped at the most recent 20 entries; `profileWarnings` and `/alternatives` are premium-only (empty / 403 for free accounts). All of this is enforced in `ProductLookupService`, `ContributionService`, and `ScanService` — the mobile client only displays what the server decided.

**Rate limiting**: `Program.cs` configures ASP.NET Core's built-in rate limiter (`Microsoft.AspNetCore.RateLimiting`, no extra package needed) at two layers — a global 100 requests/minute-per-IP limit as blunt flood defense across every endpoint, and a stricter 10 requests/minute-per-IP policy (`[EnableRateLimiting("auth")]`) on `POST /auth/device` specifically. That endpoint is unauthenticated by necessity (it's how a device *gets* a token) and creates a new `AppUser` row for any unrecognized device ID — without its own limit, a client could mint unlimited free accounts by sending a new random device ID per request, and each fresh account gets its own 10-scan/day allowance, defeating the daily-limit abuse control above entirely. Verified with a live burst test: requests 1-10 return 200, 11+ return 429 within the same window. **Caveat**: partitioned by `HttpContext.Connection.RemoteIpAddress` — if this API ends up behind a reverse proxy/load balancer in production, `UseForwardedHeaders()` must also be configured, or every request will appear to share the proxy's IP and get rate-limited together as one client. This is IP-level flood protection, not a substitute for a real edge/WAF layer (e.g. Cloudflare) in front of a production deployment — worth adding one before real traffic. (Note: `GET /products/{barcode}`, not this endpoint, is the one that fans out to Open Food Facts on cache misses — see the milestones section's "Open Food Facts rate-limit protection" entry for the fix guarding *that* outbound call specifically, a separate, much tighter limit than anything configured here.)

**Global exception handling**: `Program.cs` wires `app.UseExceptionHandler(...)` right after the Serilog request-logging middleware, catching anything unhandled anywhere downstream. Without it, an unexpected bug (one we haven't found yet) would reach the client as a bare, bodyless 500 — Kestrel's default with no handler configured — and might not get logged with full detail either. Now every unhandled exception is logged (message + stack trace) and the client gets a consistent `application/problem+json` body; the response never includes the exception's own message or stack trace, only a generic "An unexpected error occurred." — full detail goes to the log, not to API clients.

Run tests:

```bash
cd backend
dotnet test
```

Secrets (connection strings, JWT signing key, etc.) are never committed. Use `dotnet user-secrets` locally and environment variables in deployed environments. See `src/Blacklabel.Api/appsettings.Example.json` for the expected keys.

## ETL importer (`backend/tools/OffImporter`)

A standalone console tool (§8) that bulk-loads target-market products from the Open Food Facts full data dump, instead of relying on the API's one-barcode-at-a-time cache-on-lookup path. It streams the dump line by line (`Dump/DumpLineReader.cs`) — the file is gigabytes in size and is never buffered into memory — decompressing on the fly if the source ends in `.gz`. Each line is filtered by `Blacklabel.Application.Etl.TargetMarketFilter` (pure/unit-tested) to Turkey, the United States, Canada, or Europe (EU/EEA + UK + Switzerland): a GS1 barcode prefix in a known range for Turkey/US/Canada (`868`-`869`, `000`-`139`, `754`-`755`), OR a `countries_tags` entry naming one of those countries — Europe is matched by country tag only, since a manufacturer's GS1 prefix (e.g. Germany's `400`-`440` block) doesn't reliably indicate which European markets a product is actually sold in, unlike the two North American ranges. Matches are mapped through the same `ProductFromOffMapper` the live `GET /products/{barcode}` path uses (extracted from `ProductLookupService` in M8 so both stay in sync), then upserted by barcode — an existing row is updated in place rather than duplicated, so re-running the importer against the same or a newer dump is safe. **Note:** this filter only controls which products get proactively pre-seeded into the database; it has no effect on product *availability* — `GET /products/{barcode}` already falls back to a live Open Food Facts lookup (and caches the result) for any barcode not in this pre-seeded set, so a user in any country can scan any product with no functional gap, just a slightly slower first lookup outside the pre-seeded markets.

```bash
cd backend/tools/OffImporter
dotnet user-secrets set "ConnectionStrings:DefaultConnection" \
  "Server=localhost,1433;Database=Blacklabel;User Id=sa;Password=YourStrong!Passw0rd;TrustServerCertificate=True"
dotnet run
```

Configuration lives in `appsettings.json` under the `OffImporter` section:

- `DumpSource` — a local file path or an `http(s)` URL, `.jsonl` or `.jsonl.gz`. Defaults to the official Open Food Facts export (`https://static.openfoodfacts.org/data/openfoodfacts-products.jsonl.gz`); override for local testing with a small sample file, or to point at a different snapshot.
- `BatchSize` — how many matched products to accumulate before calling `SaveChanges` (default 200). The change tracker is cleared after every save so memory stays bounded across a multi-million-line dump even though only the target-market subset is ever tracked.
- `ProgressIntervalLines` — how often (in dump lines processed, not just matches) to print a progress line to the console (default 5000).

`ConnectionStrings:DefaultConnection` is required and, like the API, is never read from `appsettings.json` — set it via `dotnet user-secrets` (own `UserSecretsId`, separate from the API's) or the `ConnectionStrings__DefaultConnection` environment variable. Ctrl+C stops the importer cleanly; batches already saved before the interrupt stay committed, so resuming is just running it again. Not exercised end-to-end in this environment (no reachable SQL Server — see the backend Docker note above); verified via `dotnet build`, the streaming reader's own unit tests (plain and gzip fixtures), and an EF Core InMemory integration test asserting the upsert is idempotent across two runs of the same barcode.

## Mobile

Requirements: Node.js, Expo CLI (via `npx`), a physical device or emulator with a camera (barcode scanning does not work in the web/Expo Go simulator without a camera).

```bash
cd mobile/blacklabel
cp .env.example .env      # adjust EXPO_PUBLIC_API_URL — use your LAN IP for a physical device
npm install
npx expo start
```

Screens: **Scanner** (`app/index.tsx`) — full-screen camera, EAN-13/EAN-8/UPC-A detection, haptics, recent-scans strip, a manual barcode entry modal for when the camera can't read a code (damaged label, poor lighting, or a platform where camera scanning doesn't work at all — see the web note above), links to Compare/History/Preferences/Settings; **Compare** (`app/compare.tsx`, premium) — scan up to 5 products in a row without leaving the camera, see them sorted best-to-worst in a bottom panel with the top pick highlighted, a per-category comparison summary, and a "best for you" pick that's withheld (not just wrong) when no scanned product is safe for everyone in the household; free accounts get an upsell instead of the camera; **Result** (`app/product/[barcode].tsx`) — score ring, additives/nutrition/ingredients tabs, per-household-profile warnings, alternatives section (premium, with upsell for free accounts), loading/error/not-found/daily-limit states; **History** (`app/history.tsx`) — local scan history grouped by day with search, offline-first via `expo-sqlite`; **Preferences** (`app/preferences/`) — a household-profile list (`index.tsx`) plus a per-profile edit screen (`[profileId].tsx`: allergens to flag, diet flags, additives to avoid); **Paywall** (`app/paywall.tsx`) — feature list, RevenueCat packages, purchase/restore; **Settings** (`app/settings/`) — language switch, account/device ID, premium status, Apple/Google account linking, danger-zone account deletion, and the required **Data Sources** (`data-sources.tsx`, OFF/ODbL + vision + RevenueCat attributions), **Privacy** (`privacy.tsx`), and **Terms** (`terms.tsx`) sub-pages.

**Contribute (`app/contribute/[barcode].tsx`) is disabled in v1** — the route now unconditionally redirects home (`<Redirect href="/" />`), and nothing in the app links to it (the Result screen's not-found state no longer offers an "add this product" button). The previous 3-step camera-capture implementation is in git history, not deleted, just unwired. Reason: a new product contributed via photo goes live immediately with **no moderation step** (there's no admin/review endpoint anywhere in the API — the `ContributionService` comment about "pending admin review" only applies when a second contribution targets an *existing* product), and uploaded photos are served from a public URL with no reporting or filtering — a real gap against App Store Guideline 1.2 (User Generated Content), not just a nice-to-have. The backend endpoint (`POST /products/{barcode}/contribute`) and `ContributionService` are untouched for a v2 that adds real moderation.

Device auth (`src/auth/deviceAuthClient.ts`) generates and persists a device ID and JWT in `expo-secure-store`, fetched eagerly on app launch and attached automatically to every API call (`src/api/authorizedClient.ts`). Every scan is written to a local SQLite database immediately (`src/db/scanHistory.ts`, offline-capable) and opportunistically batch-synced to the backend (`src/sync/syncScans.ts`) — though in practice `GET /products/{barcode}` already records the authoritative scan server-side, so the local copy is marked synced immediately to avoid double-counting, and the sync path exists for genuinely-offline captures; viewed products are cached locally too (`src/db/productCache.ts`) so History can show names without a network round trip. All user-facing text lives in `src/i18n/locales/{en,tr}.json`.

RevenueCat (`src/purchases/purchases.ts`) is configured on launch with `EXPO_PUBLIC_REVENUECAT_IOS_KEY`/`EXPO_PUBLIC_REVENUECAT_ANDROID_KEY` and our backend's user id as the RevenueCat `appUserID`, so the webhook can tie purchase events back to the right account. Leave the keys blank to run without purchases configured — the Paywall shows a "not available" state instead of crashing.

Apple/Google Sign-In (`src/auth/socialAuth.ts`) links the current device account to a real identity: `expo-apple-authentication`'s `signInAsync` (iOS only, hidden when `isAvailableAsync()` is false) and `@react-native-google-signin/google-signin`'s `signIn()` (hidden until `EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID` is set) each produce a provider identity token, which is sent to `POST /auth/link` — the backend re-verifies it against Apple's/Google's live JWKS before trusting anything in it (see the backend section above), then returns a fresh JWT that `setAuthToken` persists in place of the anonymous device token. The Settings screen's new "Linked accounts" section (`app/settings/index.tsx`) surfaces both buttons and, via `GET /me/profile` (`useProfile` hook), whichever provider is already linked. **Both packages use native code**, so this flow needs a development build or `eas build` — it will not run inside Expo Go.

**Not built / not testable here**:
- End-to-end Apple/Google Sign-In. The verification and linking code above is complete and unit-tested on the backend (fake-verifier tests in `AccountLinkServiceTests`) and typechecked/bundled on the client, but actually completing the native flow needs real credentials this environment doesn't have: an Apple Developer Program membership + registered Bundle ID (for `Auth:Apple:BundleId`), and a Google Cloud OAuth consent screen + Web/iOS client IDs (for `Auth:Google:ClientId`, `EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID`, and the `iosUrlScheme` placeholder in `app.json`) — plus a development build/EAS build to run the native modules at all.
- End-to-end RevenueCat purchases. The SDK integration and Paywall UI are code-complete, but actually buying something requires a real App Store Connect / Google Play / RevenueCat project (products, offerings, sandbox testers) that doesn't exist in this environment. `configurePurchases`/`purchasePackage`/`restorePurchases` are untested beyond typechecking and bundling.
- ~~Custom app icon and splash screen~~ **done, first pass.** No image-editing tool is available in this environment (no ImageMagick/Inkscape/sharp), but `pngjs` (already a transitive dependency) can write raw pixels, so `icon.png`/`splash-icon.png`/`android-icon-{foreground,background,monochrome}.png`/`favicon.png` were generated programmatically — the score-ring mark from `ScoreRing.tsx` (same track-gray `#E0E0E0` + "good" green `#2E7D32`) on a white/transparent background per §10's spec (neutral background, one accent color only), replacing Expo's scaffolded placeholders. This is a real, on-brand, non-generic icon — not a placeholder anymore — but it's still a first pass from a script, not a designer's work; commission real art if the mark deserves more polish before submission. `android.adaptiveIcon.backgroundColor` in `app.json` was also changed from Expo's default light-blue placeholder (`#E6F4FE`) to white to match.

- **Post-M8: household profiles (per-person warnings)** — addresses the most common critique of single-score food-scanner apps (Yuka included, confirmed it has no multi-profile mode): one blended result can't represent a household where, say, one person has a peanut allergy and another is on a low-salt diet. `UserPreference` (one row per account) was replaced with `HouseholdProfile` (many rows per account — `Id`, `Name`, plus the same allergen/avoided-additive/diet-flag fields as before), backed by `GET/POST/PUT/DELETE /api/v1/me/household-profiles`. `ProductResponse.PersonalWarnings` (one flat list) became `ProfileWarnings` (one `{ profileId, profileName, warnings }` entry per household profile — `PersonalWarningCalculator` itself is untouched, just called once per profile instead of once per account), so a single scan can now say "safe for you" and "not safe for your child" in the same response instead of picking one lens for the whole household. Mobile: Settings → Preferences is now a profile list (`app/preferences/index.tsx`) with a per-profile edit screen (`app/preferences/[profileId].tsx`, reusing the original allergen/diet/additive form); the Result screen groups warnings by profile name; Compare mode (which shows up to 5 products at once, not a 2-person comparison) conservatively flags an allergen conflict if it applies to *any* profile on the account, since it doesn't yet have a per-profile viewing lens. Verified end to end against the running API (create two profiles with different allergens, confirm one scan returns independent warnings for each, confirm an unknown allergen/additive code is rejected with 400, confirm delete/cascade work) — a real bug surfaced during this: the additive/allergen code-existence checks used FluentValidation's `MustAsync`, which ASP.NET's automatic validation pipeline cannot run (throws `AsyncValidatorInvokedSynchronouslyException` the moment a non-empty code list is submitted); fixed by validating those codes manually in `MeController` instead of relying on automatic model validation for that part. 137 backend tests pass (up from 135). Follow-up fix once multi-conflict households were actually exercised: Compare mode's "best for you" pick used to fall back to "highest score anyway" when every scanned product conflicted with *someone* on the account (e.g. sardines vs. peanut butter with one profile allergic to fish and another to peanuts) — silently recommending a product to a household member who's allergic to it. Now it shows no "best choice" at all in that case (a red "none of these work for your whole household" banner instead), and the per-category summary distinguishes a genuine tie ("Similar") from every item having *some* conflict ("None are compatible") rather than collapsing both into "Similar."
- **Post-M8: cache-miss race condition + Open Food Facts rate-limit protection** — two related fixes to `GET /products/{barcode}`'s cache-miss path, found while reasoning through what happens as concurrent traffic grows. (1) Two near-simultaneous first-ever scans of the same never-before-seen barcode both missed the cache, both fetched from OFF, and both tried to insert a `Product` with the same barcode — the loser hit the `Barcode` unique index and crashed with an unhandled `DbUpdateException`. `IProductRepository.AddOrGetExistingAsync` now catches that, clears the change tracker (so a later `SaveChangesAsync` in the same request-scoped `DbContext` — e.g. recording the scan — doesn't retry the same failed insert), and returns the winner's already-committed row instead of throwing. Not verified by an automated race per se: confirmed directly that EF Core 8's InMemory test provider doesn't enforce unique indexes at all (documented as a known InMemory limitation, not something wrong in our config), so this specific path is reasoned-correct against SQL Server's real, documented `SaveChanges` behavior rather than test-covered — see the comment in `ProductRepositoryTests.cs`. (2) Open Food Facts documents a 15 requests/minute **per IP** limit for product reads (not per user — our whole server shares that budget across every user's cache misses) and reserves the right to IP-ban a client that exceeds it, which would break lookups for everyone at once. `OpenFoodFactsRateLimiter` (a `System.Threading.RateLimiting.FixedWindowRateLimiter` singleton, capped at 12/minute — below OFF's limit, not at it) now gates every outbound call. A second, previously-unnoticed bug came with fixing this: `OpenFoodFactsClient.GetProductAsync` used to collapse *every* failure mode — genuine "OFF confirms this barcode doesn't exist" (verified: OFF returns HTTP 200 with `status: 0` for that, not a 4xx/5xx) alongside 429s, 5xx errors, timeouts, and now self-throttling — into the same `null`, which `ProductLookupService` reported as `NotFound`. A user could've been told a real product "isn't in our database" just because we were rate-limited. `IOpenFoodFactsClient.GetProductAsync` now returns a proper `OpenFoodFactsLookupResult` (`Found`/`NotFound`/`Unavailable`), and a new `ProductLookupOutcome.LookupUnavailable` maps to `503` (mobile already handles this correctly for free via its existing generic-error retry UI, distinct from the not-found screen). 141 backend tests pass (up from 138).
