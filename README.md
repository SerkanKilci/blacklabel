# Blacklabel

Barcode scanner for packaged food: analyzes ingredients, additives and allergens, and produces a 0-100 score. See the original spec for full product/API/data model details.

## Structure

```
backend/    .NET 8 Web API (Domain / Application / Infrastructure / Api) + xUnit tests
backend/tools/OffImporter/  Console ETL: bulk-imports target-market products from the OFF data dump
mobile/     Expo (React Native + TypeScript) app, expo-router navigation
```

## Backend

Requirements: .NET 8 SDK, Docker (for SQL Server), `dotnet-ef` tool (`dotnet tool install --global dotnet-ef`).

```bash
cd backend
docker compose up -d                     # starts SQL Server on localhost:1433
dotnet user-secrets set "ConnectionStrings:DefaultConnection" \
  "Server=localhost,1433;Database=Blacklabel;User Id=sa;Password=YourStrong!Passw0rd;TrustServerCertificate=True" \
  --project src/Blacklabel.Api
dotnet ef database update \
  --project src/Blacklabel.Infrastructure \
  --startup-project src/Blacklabel.Api
dotnet run --project src/Blacklabel.Api
```

API comes up at the URL printed in the console (see `src/Blacklabel.Api/Properties/launchSettings.json`), with Swagger UI at `/swagger` (use the "Authorize" button with a token from `POST /api/v1/auth/device` — **every** endpoint requires it, except the RevenueCat webhook) and a health check at `/api/v1/health`. Resources: additive dictionary (`GET /api/v1/additives`, `GET /api/v1/additives/{code}`), product lookup (`GET /api/v1/products/{barcode}`) and alternatives (`GET /api/v1/products/{barcode}/alternatives`, premium-only), contribution flow (`POST /api/v1/products/{barcode}/contribute`), device/account auth (`POST /api/v1/auth/device`, `POST /api/v1/auth/link`), profile and preferences and subscription status (`GET /api/v1/me/profile`, `GET`/`PUT /api/v1/me/preferences`, `GET /api/v1/me/subscription`), scan history (`GET`/`POST /api/v1/scans`, paginated + batch), and the RevenueCat webhook (`POST /api/v1/webhooks/revenuecat`).

By default `VisionService:Endpoint` is empty, so contributions will always come back as "vision failed" until you point it at your own vision-LLM proxy that returns the JSON shape documented in `HttpVisionService.cs`. Set it via `VisionService:Endpoint` in `appsettings.json` or an environment variable. Similarly, `RevenueCat:WebhookSecret` (a user-secret, matching the "Authorization header value" configured in the RevenueCat dashboard's webhook settings) must be set for the webhook to accept requests — it fails closed (401) when unset.

`POST /api/v1/auth/link` (Apple/Google account linking) verifies the client-supplied identity token server-side before trusting anything in it: `AppleIdentityTokenVerifier`/`GoogleIdentityTokenVerifier` (`src/Blacklabel.Infrastructure/Auth/`) fetch each provider's live JWKS via its OIDC discovery document and check signature, issuer, audience and expiry with `Microsoft.IdentityModel`; only the `sub`/`email` claims from a token that passes are ever written to `AppUser`. Audiences are configured via `Auth:Apple:BundleId`/`Auth:Google:ClientId` in `appsettings.json` (public identifiers, not secrets) — both are empty by default, and an empty audience makes that provider's verifier fail closed (every link attempt rejected) rather than skip the check, the same posture as the RevenueCat webhook secret above.

**Server-side limits (§11)**: free accounts get 10 barcode scans/day (`GET /products/{barcode}` returns 429 past that; every successful lookup — cached or freshly fetched — records the authoritative `Scan` row used for counting) and 2 label-photo analyses/day (`POST .../contribute` returns 429); scan history (`GET /scans`) is capped at the most recent 20 entries; `personalWarnings` and `/alternatives` are premium-only (empty / 403 for free accounts). All of this is enforced in `ProductLookupService`, `ContributionService`, and `ScanService` — the mobile client only displays what the server decided.

Run tests:

```bash
cd backend
dotnet test
```

Secrets (connection strings, JWT signing key, etc.) are never committed. Use `dotnet user-secrets` locally and environment variables in deployed environments. See `src/Blacklabel.Api/appsettings.Example.json` for the expected keys.

## ETL importer (`backend/tools/OffImporter`)

A standalone console tool (§8) that bulk-loads target-market products from the Open Food Facts full data dump, instead of relying on the API's one-barcode-at-a-time cache-on-lookup path. It streams the dump line by line (`Dump/DumpLineReader.cs`) — the file is gigabytes in size and is never buffered into memory — decompressing on the fly if the source ends in `.gz`. Each line is filtered by `Blacklabel.Application.Etl.TargetMarketFilter` (pure/unit-tested) to Turkey, the United States, Canada, or Europe (EU/EEA + UK + Switzerland): a GS1 barcode prefix in a known range for Turkey/US/Canada (`868`-`869`, `000`-`139`, `754`-`755`), OR a `countries_tags` entry naming one of those countries — Europe is matched by country tag only, since a manufacturer's GS1 prefix (e.g. Germany's `400`-`440` block) doesn't reliably indicate which European markets a product is actually sold in, unlike the two North American ranges. Matches are mapped through the same `ProductFromOffMapper` the live `GET /products/{barcode}` path uses (extracted from `ProductLookupService` in M8 so both stay in sync), then upserted by barcode — an existing row is updated in place rather than duplicated, so re-running the importer against the same or a newer dump is safe. **Note:** this filter only controls which products get proactively pre-seeded into the database; it has no effect on product *availability* — `GET /products/{barcode}` already falls back to a live Open Food Facts lookup (and caches the result) for any barcode not in this pre-seeded set, so a user in any country can scan any product with no functional gap, just a slightly slower first lookup outside the pre-seeded markets.

```bash
cd backend/tools/OffImporter
dotnet user-secrets set "ConnectionStrings:DefaultConnection" \
  "Server=localhost,1433;Database=Blacklabel;User Id=sa;Password=YourStrong!Passw0rd;TrustServerCertificate=True"
dotnet run
```

Configuration lives in `appsettings.json` under the `OffImporter` section:

- `DumpSource` — a local file path or an `http(s)` URL, `.jsonl` or `.jsonl.gz`. Defaults to the official Open Food Facts export (`https://static.openfoodfacts.org/data/openfoodfacts-products.jsonl.gz`); override for local testing with a small sample file, or to point at a different snapshot.
- `BatchSize` — how many matched products to accumulate before calling `SaveChanges` (default 200). The change tracker is cleared after every save so memory stays bounded across a multi-million-line dump even though only the target-market subset is ever tracked.
- `ProgressIntervalLines` — how often (in dump lines processed, not just matches) to print a progress line to the console (default 5000).

`ConnectionStrings:DefaultConnection` is required and, like the API, is never read from `appsettings.json` — set it via `dotnet user-secrets` (own `UserSecretsId`, separate from the API's) or the `ConnectionStrings__DefaultConnection` environment variable. Ctrl+C stops the importer cleanly; batches already saved before the interrupt stay committed, so resuming is just running it again. Not exercised end-to-end in this environment (no reachable SQL Server — see the backend Docker note above); verified via `dotnet build`, the streaming reader's own unit tests (plain and gzip fixtures), and an EF Core InMemory integration test asserting the upsert is idempotent across two runs of the same barcode.

## Mobile

Requirements: Node.js, Expo CLI (via `npx`), a physical device or emulator with a camera (barcode scanning does not work in the web/Expo Go simulator without a camera).

```bash
cd mobile/blacklabel
cp .env.example .env      # adjust EXPO_PUBLIC_API_URL — use your LAN IP for a physical device
npm install
npx expo start
```

Screens: **Scanner** (`app/index.tsx`) — full-screen camera, EAN-13/EAN-8/UPC-A detection, haptics, recent-scans strip, a manual barcode entry modal for when the camera can't read a code (damaged label, poor lighting, or a platform where camera scanning doesn't work at all — see the web note above), links to Compare/History/Preferences/Settings; **Compare** (`app/compare.tsx`, premium) — scan up to 5 products in a row without leaving the camera, see them sorted best-to-worst in a bottom panel with the top pick highlighted, tap any row to open its full Result page; free accounts get an upsell instead of the camera; **Result** (`app/product/[barcode].tsx`) — score ring, additives/nutrition/ingredients tabs, personal warnings, alternatives section (premium, with upsell for free accounts), loading/error/not-found/daily-limit states; **Contribute** (`app/contribute/[barcode].tsx`) — 3-step photo capture, with its own daily-limit state; **History** (`app/history.tsx`) — local scan history grouped by day with search, offline-first via `expo-sqlite`; **Preferences** (`app/preferences.tsx`) — allergens to flag, diet flags, additives to avoid; **Paywall** (`app/paywall.tsx`) — feature list, RevenueCat packages, purchase/restore; **Settings** (`app/settings/`) — language switch, account/device ID, premium status, Apple/Google account linking, and the required **Data Sources** (`data-sources.tsx`, OFF/ODbL + vision + RevenueCat attributions) and **Privacy** (`privacy.tsx`) sub-pages.

Device auth (`src/auth/deviceAuthClient.ts`) generates and persists a device ID and JWT in `expo-secure-store`, fetched eagerly on app launch and attached automatically to every API call (`src/api/authorizedClient.ts`). Every scan is written to a local SQLite database immediately (`src/db/scanHistory.ts`, offline-capable) and opportunistically batch-synced to the backend (`src/sync/syncScans.ts`) — though in practice `GET /products/{barcode}` already records the authoritative scan server-side, so the local copy is marked synced immediately to avoid double-counting, and the sync path exists for genuinely-offline captures; viewed products are cached locally too (`src/db/productCache.ts`) so History can show names without a network round trip. All user-facing text lives in `src/i18n/locales/{en,tr}.json`.

RevenueCat (`src/purchases/purchases.ts`) is configured on launch with `EXPO_PUBLIC_REVENUECAT_IOS_KEY`/`EXPO_PUBLIC_REVENUECAT_ANDROID_KEY` and our backend's user id as the RevenueCat `appUserID`, so the webhook can tie purchase events back to the right account. Leave the keys blank to run without purchases configured — the Paywall shows a "not available" state instead of crashing.

Apple/Google Sign-In (`src/auth/socialAuth.ts`) links the current device account to a real identity: `expo-apple-authentication`'s `signInAsync` (iOS only, hidden when `isAvailableAsync()` is false) and `@react-native-google-signin/google-signin`'s `signIn()` (hidden until `EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID` is set) each produce a provider identity token, which is sent to `POST /auth/link` — the backend re-verifies it against Apple's/Google's live JWKS before trusting anything in it (see the backend section above), then returns a fresh JWT that `setAuthToken` persists in place of the anonymous device token. The Settings screen's new "Linked accounts" section (`app/settings/index.tsx`) surfaces both buttons and, via `GET /me/profile` (`useProfile` hook), whichever provider is already linked. **Both packages use native code**, so this flow needs a development build or `eas build` — it will not run inside Expo Go.

**Not built / not testable here**:
- End-to-end Apple/Google Sign-In. The verification and linking code above is complete and unit-tested on the backend (fake-verifier tests in `AccountLinkServiceTests`) and typechecked/bundled on the client, but actually completing the native flow needs real credentials this environment doesn't have: an Apple Developer Program membership + registered Bundle ID (for `Auth:Apple:BundleId`), and a Google Cloud OAuth consent screen + Web/iOS client IDs (for `Auth:Google:ClientId`, `EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID`, and the `iosUrlScheme` placeholder in `app.json`) — plus a development build/EAS build to run the native modules at all.
- End-to-end RevenueCat purchases. The SDK integration and Paywall UI are code-complete, but actually buying something requires a real App Store Connect / Google Play / RevenueCat project (products, offerings, sandbox testers) that doesn't exist in this environment. `configurePurchases`/`purchasePackage`/`restorePurchases` are untested beyond typechecking and bundling.
- **Custom app icon and splash screen.** This environment has no image-editing or image-generation tool available (no ImageMagick/Inkscape/sharp — `convert` on `PATH` here is Windows' disk-conversion utility, not ImageMagick's), so the icon/splash are still Expo's default scaffolded placeholders in `assets/`. Design spec for whoever produces the real ones, per §10: clinical and calm, neutral background (white or a single gray), no decorative color — if the score ring's accent color appears at all, it's the only color in the mark. Needed: `icon.png` (1024×1024, no transparency for iOS), `android-icon-foreground.png` + `android-icon-background.png` + `android-icon-monochrome.png` (adaptive icon layers), `splash-icon.png`, `favicon.png`.

## Store submission checklist

Everything here is prepared but not executed — no App Store Connect / Play Console / EAS account exists in this environment.

- [ ] Replace `ios.bundleIdentifier` / `android.package` in `app.json` (currently `com.blacklabel.app` placeholders) with your real reverse-DNS identifiers, registered in App Store Connect and Play Console.
- [ ] Commission real icon/splash art per the spec above and replace the files in `mobile/blacklabel/assets/`.
- [ ] Have `PRIVACY.md` and `TERMS.md` reviewed by counsel for your target markets (KVKK/GDPR/store requirements), replace the placeholder contact addresses, host both at public URLs, and put those URLs in both store listings and the in-app Settings → Privacy/Terms pages if you change them from the relative in-app route.
- [ ] Set up a real RevenueCat project (products, offerings, entitlement) and put the API keys in `.env` (`EXPO_PUBLIC_REVENUECAT_IOS_KEY`/`_ANDROID_KEY`) and the webhook secret in the backend's `RevenueCat:WebhookSecret` user-secret. Verify the Paywall's per-package duration label (`paywall.duration.*`) reads correctly against your actual configured offering.
- [ ] Register a Sign in with Apple capability + Bundle ID in your Apple Developer account and set `Auth:Apple:BundleId` in the backend's `appsettings.json`; register an OAuth consent screen + Web and iOS client IDs in Google Cloud Console and set `Auth:Google:ClientId` (backend), `EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID` (`.env`), and the `iosUrlScheme` placeholder in `app.json`'s `@react-native-google-signin/google-signin` plugin config.
- [ ] Point `VisionService:Endpoint` at a real vision-LLM proxy (see `HttpVisionService.cs` for the expected contract).
- [ ] Deploy the backend somewhere reachable and set `EXPO_PUBLIC_API_URL` to that URL for production builds (not `localhost`).

Worth repeating here since it's easy to miss: this only changes which products get *pre-seeded* — it was never a correctness requirement, since `GET /products/{barcode}`'s live-fetch-and-cache fallback already gave every barcode, in every country, full coverage before this change too.
- **Post-M8: Compare mode (premium)** — `app/compare.tsx`, reachable from a new button on the Scanner screen. Scan (or manually enter) up to 5 products without leaving the camera — each one is added to a running list instead of navigating to the Result screen — and see them ranked best-to-worst in a bottom panel, with the top-scoring pick highlighted; tapping any card opens its full Result page. No new backend endpoint or data model: it calls the same `GET /products/{barcode}` the Result screen already uses (via `useQueries`, one query per scanned barcode, sharing the same `['product', barcode]` cache key so a later visit to the full Result page doesn't re-fetch), just held in a local list instead of navigated to individually. Free accounts see an upsell screen instead of the camera, matching the existing alternatives/personalWarnings premium-gating pattern (client-side check against `useSubscription()` — there's no new data exposure to gate server-side, since a free user scanning the same products one at a time through the normal Scanner already gets identical data). The manual barcode entry modal was extracted out of the Scanner screen into `src/components/ManualBarcodeEntryModal.tsx` so both screens share it. A `POST /api/v1/me/debug-grant-premium` endpoint (returns 404 outside `Development`, gated on `IWebHostEnvironment.IsDevelopment()` regardless of any other config) plus a matching dev-only button in Settings exist purely so premium screens can be tested without a real RevenueCat purchase.
- **Post-M8: per-category comparison breakdown** — each Compare card now shows *why* one product outscores another, not just that it does: a Good/Medium/Bad dot for sugar, saturated fat, salt, and additive load, plus an allergen-compatibility line sourced from the same `personalWarnings` the Result screen already computes. Critically, the bands are computed server-side in `ScoreCalculator.Calculate` (new `ComparisonLevel` classification, exposed via `ScoreResult` → `ProductResponse.ComparisonBands`) from the *exact same* `ScoreThresholds`/additive-risk-point values that produce the numeric score — never a separately-invented client-side threshold — so a card can never say "sugar: low" while the score reflects otherwise. The "best choice for you" banner at the top of the list isn't just the highest score: it excludes any product with an active allergen conflict first, so a higher-scoring product you're allergic to never gets recommended to you. `CalculateAdditivesScore`'s risk-point table was refactored into a shared private helper (`AdditivePenaltyPoints`) reused by both the score deduction and the new "Few/Some/Many" additive band, so the two can't drift apart either. 12 new backend unit tests cover the classification boundaries.
